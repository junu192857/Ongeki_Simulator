# 온게키 시뮬레이터 채보 형식 명세

> 버전: **v0.5 (설계 초안)** · 최종 갱신: 2026-10-19  
> 목적: OGKR의 파일 구조를 그대로 복제하는 대신, 온게키 핵심 게임플레이를 표현하는 독립 형식을 정의한다.  
> 이 문서의 '확정'은 논의된 원칙을 뜻하며, 예시 JSON의 필드명과 상세 스키마는 일부 미확정이다.

## 1. 개발 범위

**초기 구현:** METADATA, HEADER, PLATFORM, LANE, TAP/HOLD/WALL NOTE, FLICK, BELL.  
**후속 구현:** BULLET와 LASER (레이저도 탄막의 일부), 적 이동, 연출, 장식 전용 레인.

## 2. 시간·공간 좌표계 (확정)

- 시간을 `(unit, tick)` / JSON `[unit, tick]`으로 표현한다.
- **4분음표 네 개의 길이 = 1920틱**이므로 4분음표 1개는 480틱이다.
- `unit`은 마디 번호가 아니라 **고정 1920틱 단위**이고 `tick`의 정규화 범위는 0–1919이다.
- `absoluteTick = unit * 1920 + tick`; 실제 초 단위 시각은 BPM 변경 이력을 이용해 산출한다.
- 박자표 변경은 `unit` 길이를 변경하지 않는다. 예: 4/4 한 마디=1920, 6/4=2880, 6/8=1440틱.
- 캐릭터·레인·플랫폼·노트의 수평 위치는 실수 좌표로 표현한다. 수평 좌표의 원점 및 기준 폭은 미정이다.

## 3. 파일별 책임 (확정)

- **METADATA:** 곡 공통 정보. 제목, 아티스트, 음원 경로, 음원 길이, 난이도와 채보 파일 연결.
- **HEADER:** 채보별 BPM, 박자표, 레인·노트 스크롤 속도, 롱노트 중간 틱 판정 설정.
- **SETTINGS:** 사용자의 오디오 오프셋, 입력 보정 등. 채보 파일과 분리.
- 노트 총수 및 벨 총수는 레코드를 읽어서 계산한다.
- 음원 길이는 METADATA에 둔다.

### METADATA 후보 필드 (세부 스키마 미확정)

| 필드 | 타입 | 의미 |
|---|---|---|
| `title` | string | 곡 제목 |
| `artist` | string | 아티스트 |
| `audioFile` | string | 음원 상대 경로 |
| `audioLength` | number | 음원 길이, 초 단위 |
| `difficulties` | array | 난이도 이름·레벨·채보 파일 경로 |

Vexatonic Dash 2의 `METADATA.txt`에서 사용하던 NAME, ARTIST, MUSIC, LEVEL, LENGTH의 역할을 참고한다.

## 4. HEADER (구성 확정)

| 필드 | 의미 |
|---|---|
| `version` | 형식 버전 |
| `bpmChanges` | 시간별 BPM(4분음표 기준) |
| `meterChanges` | 시간별 박자표 분자/분모 |
| `scrollSpeedChanges` | 시간별 노트 및 레인 스크롤 속도 |
| `holdTickChanges` | 시간별 롱노트 중간 판정 간격 |

- 시간 분해능 1920은 파일 형식의 **고정 규칙**이므로 매 HEADER에 쓰지 않아도 된다.
- BPM, 스크롤 속도, 롱노트 틱 간격은 **서로 독립적으로 변경되는 설정**이다.
- **스크롤 속도는 노트와 레인의 표시 속도에만 적용**한다. 벨이나 탄막에 자동으로 적용하지 않는다.
- 스크롤 속도의 단위(배율/거리 단위)와 롱노트 틱 간격의 구체적인 단위(음악 틱/초)는 아직 확정되지 않았다.

예시(간격의 `intervalTicks` 필드는 잠정안):

```json
{
  "HEADER": {
    "version": "0.3",
    "bpmChanges": [{"time": [0, 0], "bpm": 180}],
    "meterChanges": [{"time": [0, 0], "numerator": 4, "denominator": 4}],
    "scrollSpeedChanges": [{"time": [0, 0], "speed": 1.0}],
    "holdTickChanges": [{"time": [0, 0], "intervalTicks": 240}]
  }
}
```

## 5. PLATFORM (핵심 규칙 확정)

플랫폼의 경계가 변하는 각 시점에 **`(시간, leftX, rightX)`** 키프레임을 저장한다. 인접 키프레임 사이의 좌우 경계는 각각 독립적으로 **3차 베지어(Cubic Bézier)** 보간한다.

- 경계마다 제어점 두 개를 갖는 구간 모델을 사용한다.
- **구체적인 데이터 표현 제안:** 두 내부 제어점의 시간 좌표는 구간의 1/3, 2/3에 고정하고 X좌표만 저장한다. 시작 키프레임의 `leftControlOut/rightControlOut` 및 다음 키프레임의 `leftControlIn/rightControlIn` 필드로 표현한다.
- `u = (currentTick - startTick)/(endTick - startTick)` (0–1)에 대해 위치는 아래처럼 보간한다.

```text
B(u) = (1-u)^3·P0 + 3(1-u)^2·u·P1 + 3(1-u)·u²·P2 + u³·P3
```

- 제어점이 시작점과 끝점 사이의 1/3, 2/3 위치에 일직선으로 놓이면 직선 보간도 표현 가능하다.
- **플랫폼 경계는 캐릭터의 물리적인 이동 가능 범위를 벗어날 수 있다.** 데이터 로딩·보간·렌더링에서 그 범위로 강제 제한하지 않는다.
- **캐릭터 위치 보정이 적용되는 시간 구간은 경계 키프레임과 별도로 저장**한다. 보정 구간 밖에서는 플랫폼 경계만을 이유로 캐릭터 좌표를 강제 보정하지 않는다.

예시(필드명 잠정):

```json
{
  "PLATFORM": {
    "points": [
      {
        "time": [0, 0], "leftX": -5.0, "rightX": 5.0,
        "leftControlOut": -4.0, "rightControlOut": 4.0
      },
      {
        "time": [1, 0], "leftX": -3.0, "rightX": 3.0,
        "leftControlIn": -2.0, "rightControlIn": 2.0
      }
    ],
    "correctionIntervals": [
      {"startTime": [0, 0], "endTime": [1, 0]}
    ]
  }
}
```

**미정:** 보정 방식과 경계 포함 여부, 제어점 필드 최종 명칭, 경계 불연속·교차·구간 밖 처리, 단일 키프레임 처리.

## 6. LANE (기본 구조 확정)

레인은 **(ID, 색상, 시간, X좌표)** 를 기반으로 정의한다. 하나의 레인 객체는 하나의 연속 구간만 표현하며, 키프레임 사이의 X좌표는 Cubic Bézier로 보간한다.

- `id`는 **채보 전체에서 유일**하며, 종료된 레인의 ID도 **절대 재사용하지 않는다**. **ID 0은 좌측 벽 레인, ID 1은 우측 벽 레인으로 예약**하고, 일반 레인은 **ID 2 이상**을 사용한다. 같은 색상의 일반 레인이 동시에 여럿 존재할 수 있다.
- `color`는 레인 객체의 속성이며 초기 구현의 일반 레인은 `RED`, `GREEN`, `BLUE`를 사용한다. 장식 전용 레인은 초기 구현에서 제외한다.
- `points`는 `{time, x}` 키프레임 목록이다. 첫 점은 해당 레인의 시작, 마지막 점은 종료를 뜻한다.
- **레인이 끊기거나 사라지는 경우 기존 레인을 종료**하고, 이후 다시 나타나면 **새 ID의 별도 레인**을 만든다. 하나의 레인에서 불연속된 시간 구간을 표현하지 않는다.
- 플랫폼과 공통의 **Cubic Bézier** 보간 계산을 사용한다. 시작 키프레임의 `controlOut`, 다음 키프레임의 `controlIn`을 구간 제어점 X값으로 사용하는 형식은 현재의 세부 표현안이다.
- **벽 레인은 플랫폼의 왼쪽(ID 0)·오른쪽(ID 1) 경계를 항상 따라 각각 하나씩 존재하는 가상 레인**이다. 일반 `LANES` 목록에 별도 키프레임을 중복 기록하지 않으며, 어느 시각이든 플랫폼 좌·우 경계의 보간 결과를 이용한다.
- 노트는 벽 레인과 일반 레인을 **동일한 `laneId` 필드**로 참조한다. ID 0/1은 플랫폼 경계에서 위치를 조회하고, ID 2 이상은 `LANES` 객체에서 위치를 조회한다.
- 일반 레인 데이터에서 ID 0 또는 1을 선언하는 것은 허용하지 않는다.
- 벽 레인은 플랫폼의 경계가 캐릭터의 이동 가능 범위를 벗어나도 해당 경계를 그대로 따른다.

예시(제어점 필드명은 잠정안):

```json
{
  "LANES": [
    {
      "id": 2,
      "color": "RED",
      "points": [
        {"time": [0, 0], "x": -2.0, "controlOut": -1.0},
        {"time": [1, 0], "x": 1.0, "controlIn": 0.0}
      ]
    },
    {
      "id": 3,
      "color": "RED",
      "points": [
        {"time": [2, 0], "x": 1.0, "controlOut": 1.0},
        {"time": [3, 0], "x": -1.0, "controlIn": -1.0}
      ]
    }
  ]
}
```

위 예시에서 2번 레인은 `[1, 0]`에 종료되며, 같은 색의 레인이 다시 나타나더라도 2번 ID를 사용하지 않고 3번으로 정의한다.

**미정:** 한 점짜리 레인의 처리, 레인 시작·종료 시각의 포함 규칙, 베지어 핸들의 기본값과 최종 직렬화 명칭.

## 7. NOTES (기본 구조 확정, 판정 세부 규칙은 예정)

노트는 **레인 참조 여부**(LANE / FREE)와 **종류**(TAP / HOLD) 두 축에 따라 **네 개의 구체적인 자료형**으로 구분한다. 공통 부모 `NoteData`가 공유 데이터를 제공하고, 각 하위 자료형은 자신에게 필요한 경로 데이터와 동작을 갖는다.

```text
NoteData (abstract)
├── LaneTapData
├── LaneHoldData
├── FreeTapData
└── FreeHoldData
```

### 7.1 공통 노트 필드

| 필드 | 설명 |
| --- | --- |
| `time` | 시작/판정 시간 `[unit, tick]` |
| `color` | 노트 색상/판정 버튼(정확한 enum 추후 확정) |
| `adjusted` | 판정 보정 여부(boolean) |

- 타입 식별자(`kind`, `anchor` 등)의 **JSON 직렬화 방식은 추후 확정**한다. 네 종류가 역직렬화 시 명확히 구별되어야 한다.
- 각 노트 자료형의 저장용 **데이터 모델**과 실제 입력·판정을 수행하는 **런타임 로직**은 분리할 수 있다. 상속 계층을 통해 롱노트에만 필요한 홀드 시작·유지·종료 판정과 노트 종류별 위치 조회 메서드를 분리하는 방향으로 구현한다.
- 아래 예시에서 `kind`는 설명을 위한 임시 구분자다.

### 7.2 네 가지 자료형

| 자료형 | 고유 필드 | 위치/경로 결정 |
| --- | --- | --- |
| `LaneTapData` | `laneId` | 판정 시각에 해당 레인의 X |
| `LaneHoldData` | `laneId`, `endTime` | 시작부터 종료까지 참조 레인의 경로 |
| `FreeTapData` | `x` | 판정 시각의 고정 X |
| `FreeHoldData` | `points[]` | 자체 Cubic Bézier 경로 |

- `laneId`는 레인 종속 노트에만 존재한다. **0=좌측 벽, 1=우측 벽, 2 이상=일반 레인**.
- 자유 위치 노트에는 `laneId`를 기록하지 않는다.
- **자유 롱노트의 `points[]`는 시작점과 끝점을 반드시 모두 포함**하며, 각 원소에 `time`과 `x`를 기록한다. 중간 관절도 필요에 따라 추가한다.
- 자유 롱노트의 시작 시각은 `points[0].time`과 일치해야 하고, 끝 시각은 마지막 점의 `time`으로 결정한다. 중복되는 별도 `endTime`은 필수가 아니다.
- 자유 롱노트 경로에는 플랫폼 및 일반 레인과 공유하는 **Cubic Bézier 보간**을 사용한다. 핸들의 최종 직렬화 방식은 추후 확정한다.
- 레인 종속 노트의 시간은 해당 레인의 유효 기간 안에 있어야 하고, `LaneHoldData`는 종료 시각까지 유효한 레인을 참조해야 한다. 가상 벽 레인은 플랫폼 경계로부터 조회한다.

### 7.3 JSON 구조 예시 (잠정)

```json
{
  "NOTES": [
    {
      "kind": "LANE_TAP", "time": [2, 480],
      "color": "RED", "adjusted": false, "laneId": 2
    },
    {
      "kind": "LANE_HOLD", "time": [3, 0], "endTime": [4, 960],
      "color": "BLUE", "adjusted": false, "laneId": 3
    },
    {
      "kind": "FREE_TAP", "time": [5, 0],
      "color": "GREEN", "adjusted": false, "x": -1.5
    },
    {
      "kind": "FREE_HOLD", "time": [6, 0],
      "color": "RED", "adjusted": false,
      "points": [
        {"time": [6, 0], "x": -2.0, "controlOut": -1.5},
        {"time": [7, 0], "x": 1.0, "controlIn": 0.5}
      ]
    }
  ]
}
```

### 7.4 FLICK (상세 정의 예정)

플릭은 판정 시간, 좌측 끝·우측 끝, 방향을 가진다. 플릭은 일반 탭/홀드 네 종류와 별도 계열로 취급하며, 실제 판정 영역과 상속 관계는 추후 정의한다.

**미정:** 노트 색상 enum 및 벽 노트 버튼 표현, 롱노트 틱 판정 로직, 입력 보정 의미, 자유 롱노트 시간 중복 필드의 최종 정리, JSON 식별자, 플릭 판정 규칙.

## 8. BELL (상세 정의 예정)

- 후보 데이터: 시작·끝 시각, 시작·끝 X좌표, 속도.
- 벨 이동 시스템은 우선 HEADER 스크롤 속도와 별도로 정의한다.
- 이동 속도와 시간·위치 값이 중복으로 제약될 수 있으므로 기준값과 파생값의 관계를 추후 결정한다.
- 원본 OGKR의 팔레트·이동 규칙과 실제 게임 동작을 확인해 보완한다.

## 9. BULLET / LASER (초기 범위에서 제외)

탄막은 가장 복잡한 시스템이므로 초기 구현에서 제외한다. **레이저 역시 탄막 시스템의 일부**로 보고 같은 후속 단계에 함께 추가한다.
